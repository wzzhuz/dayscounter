## 为什么改

**背景**：一直在用「倒数日 · Days Matter」记录重要日子。它是免费榜 Top 1 的产品，功能做得不错，但商业模式卡在使用体验上。

**使用者的原话**：「高级功能收费，且存在一定广告，想要自己实现一个。」

具体卡住的点（2026 年现状）：

| 限制 | 实际情况 |
|---|---|
| 事件数量 | 免费版**限 20 条**，超出要订阅 |
| 广告 | 免费版带 banner 广告，这是使用者明确提到的痛点 |
| 周期重复提醒 | 生日/纪念日按年重复需订阅解锁 |
| 高级背景模板 | 需订阅解锁 |
| 定价 | Pro 买断 ¥32；订阅 ¥3/月；另有「重置密码 ¥3」「相册 1000 张 ¥5 / 10000 张 ¥40」 |
| 云同步 | 需注册 iCity 账号，**数据存在厂商服务器上** |

对于一个只给自己用、数据只有几十条的工具，为这些付费不划算；而免费版的广告和 20 条上限又天天硌着。

**问题**：没有替代物。需要的其实很窄——把「某一天距今多少天」这件事算对、看清、并能放在桌面上，其余什么都不需要。

## 做什么

1. 新建独立仓库 `dayscounter`，建立 `openspec/` 结构（`project.md`、`AGENTS.md`、`specs/`）
2. 实现**天数计算核心**（`specs/day-count/`）
   - 倒数与累计双向计算（**含计数模式口径**：倒数不含起始日 / 正数包含起始日）
   - 农历（农历日期 ↔ 公历日期互转）
   - 按年重复事件的下一次发生日推导
3. 实现**事件管理**（`specs/event-management/`）
   - 事件的增删改查
   - 分类（纪念日 / 工作 / 生活 + 自定义）
   - **标签（多对多）**
   - **全文搜索**（标题 + 备注，SQLite FTS4）
   - 置顶与排序
4. 实现**本地持久化**（`specs/data-persistence/`）
   - **Room（SQLite）** 作为存储层，事务保证原子性
   - JSON 作为**交换格式**做导出 / 导入
   - Entity 预留 `reminderDaysBefore` 字段，供后续提醒 change 使用
5. 搭 Kotlin + Jetpack Compose 工程骨架，配 GitHub Actions 出 debug APK

## 不做什么

- ❌ **不做桌面小组件** —— 单独开 `add-home-widget` change。小组件是这类 App 的灵魂，但依赖 Glance，有自己的能力边界和崩溃风险（用错会运行时崩溃，编译期发现不了）。**数据库 Schema 已支持**，开 change 时无需迁移
- ❌ **不做到期通知提醒** —— 单独开 `add-event-reminder` change。需要通知权限、渠道适配、WorkManager 时机。**`reminderDaysBefore` 字段已在 Entity 预留**，开 change 时无需迁移
- ❌ **不做云同步 / 账号** —— 违反「数据是你的」铁律，且引入后端复杂度
- ❌ **不申请任何网络权限** —— 代码里连 `INTERNET` 都不声明（沿用 lifelog 铁律）
- ❌ **不做自定义背景图 / 壁纸 / 分享海报** —— Days Matter 的付费点，但自用场景无感
- ❌ **不做农历以外的历法**（如农历节气精确时刻、回历）
- ❌ **不做「历史上的今天」「日期计算器」** —— 附属玩具功能，不解决核心诉求
- ❌ **不做按月 / 按周重复** —— 首版只做按年重复（覆盖生日、纪念日这两个真实场景），按月按周等实际需要时再补
- ❌ **不做数据加密 / 密码保护** —— 自用场景，换机靠导出导入

## 对齐结论

> 阶段 0 在对话里产出，五项齐全才进入写作。
> 写进这里是为了：下次会话不必重新讨论。

1. **要解决什么问题**
   把 Days Matter 里真正用得上的功能（倒数/累计、分类置顶、按年重复、农历），用零广告、零订阅、零事件数上限的方式自己实现一遍。数据只有几十条，不值得为它付费，但免费版的广告和 20 条上限天天硌着。

2. **范围边界**
   - 改（做）：天数计算核心（含农历、按年重复）、事件管理（CRUD / 分类 / 置顶排序）、本地 JSON 持久化 + 导出导入、Android 工程骨架
   - 不改（不做）：小组件、通知提醒、云同步、网络权限、自定义背景、按月按周重复、日期计算器
   - 详见上文「做什么」「不做什么」两节

3. **关键约束**
   - 平台：**Android 原生**，Kotlin + Jetpack Compose
   - 出包路径：沙盒不能编译 APK → 写源码推 GitHub → Actions 编译（沿用 lifelog 已验证链路）
   - 存储：**Room（SQLite）**，JSON 仅作导出/导入的交换格式
   - 数据：**纯本地，不申请任何网络权限**
   - 农历：**要支持**（家人生日、春节的真实场景）
   - 计数口径：**倒数不含起始日**（明天=1 天）；**正数包含起始日**（出生当天=第 1 天）
   - 跨时区：**不做处理**，一律按设备本地时区取「今天」
   - 库里**只存事实**：剩余天数、下一次发生日均不落库，读取时推导

4. **验收标准**（可测）

   - **GIVEN** 今天是 2026-09-16，事件目标日为 2026-09-16，模式为倒数
     **WHEN** 查看该事件
     **THEN** 显示 **0 天**，且标记为「就是今天」

   - **GIVEN** 事件目标日为 2026-09-17（明天），模式为倒数
     **WHEN** 查看该事件
     **THEN** 显示 **还剩 1 天**

   - **GIVEN** 事件目标日为 2020-01-01（已过去），模式为倒数
     **WHEN** 查看该事件
     **THEN** 显示 **已过 N 天**（N = 纯日期差），不显示为负数

   - **GIVEN** 事件为「宝宝出生」，目标日就是今天，模式为正数
     **WHEN** 查看该事件
     **THEN** 显示 **第 1 天**（`N = |日期差| + 1`）

   - **GIVEN** 一个倒数模式的春节事件，已过去 2 天
     **WHEN** 查看该事件
     **THEN** 显示「已过 2 天」
     **AND 不显示**「春节第 3 天」（模式不得自动切换）

   - **GIVEN** 某事件备注中含「血常规正常」
     **WHEN** 搜索「血常规」
     **THEN** 该事件出现在结果中

   - **GIVEN** 事件 A 被打上「家人」「重要」两个标签
     **WHEN** 按标签「家人」筛选
     **THEN** A 出现在结果中
     **AND** 按「重要」筛选同样能找到 A

   - **GIVEN** 删除一个带标签的事件
     **WHEN** 检查关联表
     **THEN** 对应关联行已被级联清理，无孤儿行

   - **GIVEN** 一个按年重复的事件，原始日期为 2000-02-29
     **WHEN** 当前年份非闰年（如 2027）
     **THEN** 该年发生日推导为 **2027-02-28**，不崩溃、不跳过该年

   - **GIVEN** 一个农历事件，日期为农历二〇二六年八月十五
     **WHEN** 转换为公历
     **THEN** 得到 2026-09-25（需以农历校验表核对，见 `design.md` 风险段）

   - **GIVEN** 存有 1000 条事件
     **WHEN** 冷启动加载并渲染列表
     **THEN** 首帧渲染在可感知范围内完成
     **AND** 列表滚动无明显掉帧（不得在 `items{}` 内做 `indexOfFirst` / `find` / `sortedBy`）

   - **GIVEN** 修改 1 条事件的标题
     **WHEN** 检查实际执行的 SQL
     **THEN** 为单条 `UPDATE`，**未重写**整个数据集

   - **GIVEN** 导出 JSON 文件
     **WHEN** 在另一台设备（或清数据后）导入该文件
     **THEN** 事件数量、标题、日期、历法、计数模式、重复规则、分类、**标签关联**、置顶状态、备注**全部还原**

   - **GIVEN** 导入一个第 50 条格式错误的 JSON
     **WHEN** 导入出错
     **THEN** **全部回滚**，一条都不写入，且保留导入前的数据

   - **GIVEN** 写入过程中进程被杀
     **WHEN** 再次启动
     **THEN** 数据回滚到上一个一致状态，无半截数据

   - **GIVEN** 反编译或检查 AndroidManifest.xml
     **WHEN** 检查权限声明
     **THEN** 不存在 `android.permission.INTERNET`

5. **被否决的方案**
   一句话结论：**单文件 JSON 存储被推翻**（原为采纳），改用 Room；
   ProtoBuf / DataStore、SQL 内排序、预生成重复事件实例、靠日期自动判定计数口径均被否决。
   完整对比与**推翻 JSON 的完整论证**见 `design.md` 第零节与第七节。

## 已解决的关键分歧

| # | 分歧 | 结论 | 说明 |
|---|---|---|---|
| 1 | 用 JSON 还是 Room 存 | **Room** | 首版判定 JSON 够用，经重测后推翻。论证见 `design.md` 第零节 |
| 2 | 「出生当天算第 1 天」与「还剩 N 天」冲突 | **引入 `countMode` 字段** | 倒数不含起始日、正数包含起始日。不靠日期自动推断，否则过期春节会变成「春节第 3 天」 |
