# 设计决策

## 一、事件库：内置数据从哪来

| 方案 | 否决理由 |
|---|---|
| 网络拉取节日 API | **违反铁律二**（不申请网络权限），且离线不可用 |
| 自建数据表 + 自己算 | 选这个。农历节日存「农历月日」，每年用 `LunarCalendar` 现算，与已有重复逻辑同源 |
| 写入农历对照表硬编码公历日期 | 否决。硬编码 2027 年的春节公历日期，2028 年就错了，属于「数据腐败」 |

**关键**：事件库**不存具体年份的公历日期**，只存规则：

```kotlin
LibraryItem(
    name = "春节",
    kind = LUNAR,           // 或 GREGORIAN
    month = 1, day = 1,     // 农历正月初一
    suggestedCategory = "节日",
    repeatYearly = true,
)
```

添加时才调 `LunarCalendar.lunarDateInYear(1, 1, 当前年)` 换算成具体日期。
这样 2027、2028 年都能自动算对，**不需要维护一张逐年对照表**。

### 不收录周规则类节日

母亲节（5 月第 2 个周日）、父亲节（6 月第 3 个周日）、感恩节（11 月第 4 个周四）
这类需要「第 N 个星期 X」规则，与现有 `RepeatType`（NONE / YEARLY）不匹配。

**决定不收录**。理由：加了这类规则要动 `DayCountCalculator.nextOccurrence` 的核心推导，
而收益只是多三个节日——**性价比不成立**。缺的日子用户可以手打，三步照样完成。

## 二、归档：软删除还是硬删除

**选软删除**。加 `archivedAt: Long?` 字段，NULL = 未归档。

- 主列表查询加 `WHERE archivedAt IS NULL`
- 归档页单独查询 `WHERE archivedAt IS NOT NULL`
- 恢复 = 置回 NULL；彻底删除 = 真 DELETE

**为什么不用单独的归档表**：跨表移动要事务保证原子性，
且导出时两张表要分别处理。单字段最简单，且 Room 索引能直接覆盖。

**导出必须包含归档事件**：换机时如果丢了归档，
等于「归档」这个动作骗了用户——他以为留着，其实没了。

## 三、配色：怎么做到「好看」而不踩坑

### 3.1 分类主题色

三个默认分类各配一组**柔和渐变**（低饱和背景 + 中饱和强调色），
保证白字/黑字都能读。不用高饱和，因为卡片里要放数字，高饱和会让数字糊掉。

| 分类 | 起始色 | 结束色 |
|---|---|---|
| 纪念日 | `#FCE4EC` 粉 | `#F8BBD0` |
| 工作 | `#E3F2FD` 蓝 | `#90CAF9` |
| 生活 | `#E8F5E9` 绿 | `#A5D6A7` |
| 节日 | `#FFF3E0` 橙 | `#FFCC80` |
| 自定义 | 从调色板轮转分配 | |

自定义分类用 `name.hashCode() % palette.size` 分配——
**同一个分类名永远得到同一个颜色**，不会出现重启 App 变色的情况。

### 3.2 为什么不用 Material3 动态配色（Android 12+ 取壁纸色）

否决。动态配色（Material You）只在 Android 12+ 生效，
且取色结果不可控——用户的壁纸如果是深色，卡片文字对比度可能不达标。
**好看的前提是能看清**，固定调色板更稳。

### 3.3 事件可覆盖分类色

每个事件存 `colorArgb: Int?`，NULL = 跟随分类色。
给个性化留口子，但不强制——**默认就好看**是首位的。

## 四、日期计算器：算什么

两个能力，一个页面两个 Tab：

1. **间隔**：两日期相差多少天。除总天数外，额外给「X 年 Y 月 Z 天」的分解
2. **推算**：某日期前/后 N 天是哪天

**为什么用 `ChronoUnit.DAYS.between` 而不是自己算**：
`LocalDate` 的 `toEpochDay()` 相减已经是纯日期差，不含时区与夏令时。
`ChronoUnit.DAYS.between` 内部就是这个实现，**没有理由自己写**。

「X 年 Y 月 Z 天」的分解用 `Period.between`，但要注意：
`Period.between(2026-01-31, 2026-03-01)` 得 `1月1天`（不是 29 天），
这是 `Period` 的语义（按日历单位逐字段算），**属正常，不是 bug**，UI 上标注为「约」。

## 五、否决的方案

| 方案 | 否决理由 |
|---|---|
| 事件库走网络 | 违反铁律二 |
| 事件库硬编码逐年公历日期 | 数据会过期腐败 |
| 归档用独立表 | 跨表移动需事务，导出变复杂 |
| Material You 动态配色 | 取色不可控，可能影响可读性 |
| 自定义背景图（相册） | 需相册权限，与铁律二冲突 |
| 收录母亲节等周规则节日 | 要改核心推导，收益不匹配 |

## 六、风险

| 风险 | 缓解 |
|---|---|
| 农历节日换算错 1 天 | 沿用已验证的 ICU `ChineseCalendar`；事件库加春节/中秋回归校验 |
| 数据库升 v3 丢数据 | 写显式 `MIGRATION_2_3`，**不用** `fallbackToDestructiveMigration` |
| 渐变色影响文字可读性 | 固定低饱和背景 + 深色文字，不用高饱和 |
