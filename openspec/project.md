# 倒数日 · 项目约定

> 本文件是 `dayscounter` 的项目铁律。任何改动不得违反。
> 流程规范本身见 [wzzhuz/my-app-workflow](https://github.com/wzzhuz/my-app-workflow)。

## 这是什么

一个只给自己用的倒数日 App：记录重要日子，显示「还剩多少天」或「已过多少天」。

**为什么自己造**：Days Matter 免费版限 20 条事件、带广告，周期重复提醒与高级模板需订阅
（Pro 买断 ¥32 / 订阅 ¥3/月）。自用场景数据量只有几十条，为这些付费不划算。

## 三条铁律

1. **天数必须算对** —— 口径一旦定下就写进 spec，任何 UI 美化不得改变计算逻辑
2. **数据是你的** —— 不申请任何网络权限，数据不出设备
3. **记录成本必须低** —— 加一条事件最快路径是三步以内（标题 → 日期 → 保存）

## 技术栈

| 项 | 选型 | 理由 |
|---|---|---|
| 平台 | Android 原生 | 后续要做桌面小组件，只有原生能做 |
| UI | Kotlin + Jetpack Compose + Material3 | 与 lifelog 一致，复用已验证链路 |
| 存储 | **Room（SQLite）** | 局部 UPDATE、索引查询、FTS 全文搜索、外键级联。迁移成本此刻为零 |
| 交换格式 | JSON（仅用于导出/导入） | 人可读，换机拷文件即可 |
| 农历 | `android.icu.util.ChineseCalendar` | 系统内置（API 24+），零依赖 |
| 序列化 | kotlinx.serialization | 仅用于导出/导入的 JSON |
| 出包 | GitHub Actions | 沙盒无 Android SDK |

**明确不引入**：任何网络库、广告 SDK、统计 SDK、崩溃上报 SDK。

## 已确认不做

- ❌ 云同步 / 账号系统 —— 违反铁律 2，且引入后端复杂度
- ❌ 网络权限 —— 连 `INTERNET` 都不声明
- ❌ 广告与内购 —— 这是自建 App 的初衷
- ❌ 事件条数上限 —— 这是自建 App 的初衷
- ❌ 按月 / 按周重复 —— 真实场景只有生日、纪念日（按年）
- ❌ 时刻（时分秒）参与天数计算 —— 引入无解边界问题，只存 `LocalDate`
- ❌ 跨时区处理 —— 明确取舍，一律按设备本地时区
- ❌ 持久化「剩余天数」或「下一次发生日」 —— 推导值不落库，读取时算
- ❌ 自定义背景图 / 分享海报 —— 自用场景无感
- ❌ 数据加密 / 密码保护 —— 换机靠导出导入

## 天数口径（核心，改动前必读）

事件带 `countMode` 字段，两种模式**有意不对称**：

| 模式 | 语义 | 今天 | 明天 | 昨天 |
|---|---|---|---|---|
| `COUNTDOWN` 倒数 | 不含起始日 | 就是今天（0） | 还剩 1 天 | 已过 1 天 |
| `COUNTUP` 正数 | 包含起始日 | **第 1 天** | 还剩 1 天 | 第 2 天 |

**不得靠「日期在过去还是未来」自动推断**——否则过期的春节会显示成「春节第 3 天」。

Compose 工程结构、Actions 出包、原子写入、固定 debug 签名。

## 规格的分工

| 路径 | 职责 |
|---|---|
| `openspec/specs/` | 系统 **SHALL** 做什么（真理源） |
| `openspec/changes/*/design.md` | 某次变更**为什么**这么选（写完即定型，不会腐化） |
| 本文件 | 长期稳定的约束 |

**决策背景不写进独立 `docs/`** —— lifelog 踩过：独立技术文档无人持续更新，
「文档写着不用 Room 而代码早已迁移」持续数个版本。历史记录天然不会腐化。
